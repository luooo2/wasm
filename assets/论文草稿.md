

# WebAssembly与原生代码的性能分析





## 摘要

WebAssembly 作为面向安全沙箱环境的低级二进制指令格式，近年来已从浏览器内执行逐步扩展到服务端、边缘计算等浏览器外场景。现有研究表明，WebAssembly 具备良好的可移植性与部署优势，但其与原生代码之间仍存在复杂且不稳定的性能差异；同时，已有工作更多关注总体跑分对比，对于性能差异背后的程序结构因素缺乏足够的可解释分析。针对这一问题，本文围绕 WebAssembly 与原生代码的性能差异展开实证研究，重点分析静态程序特征对性能差异的解释能力。

本文构建了原生代码、WebAssembly JIT 与 WebAssembly AOT 三种运行模式，基于 microbenchmark 与 PolyBench kernel 两类基准程序建立实验数据集；采用基准程序内部计时而非外部 wall-clock 计时，以获得更稳定的连续性能指标；进一步结合 LLVM IR 与源码信息，提取控制流、计算/访存比例、调用与程序规模等静态特征，并从连续性能比值 ratio 的角度对性能差异进行统计分析、回归分析与案例分析。

实验结果表明：相比离散性能标签，连续 ratio 更适合刻画 WebAssembly 与原生代码之间的细粒度性能差异；在 microbenchmark 数据集上，性能表现受局部机制与多因素耦合影响较大，当前静态特征的整体解释力较弱；在 PolyBench kernel 数据集上，`compute_density`、`ls_ratio` 与 `compute_mem_ratio` 等特征与性能差异呈现出相对稳定的关系，说明规则数值程序中的计算—访存结构对 WebAssembly 性能具有一定解释能力。同时，AOT 并未表现出稳定优于 JIT 的总体趋势，二者在结构敏感性上也较为接近。

本文的工作表明，WebAssembly 与原生代码的性能差异并不能仅通过单一跑分结果加以概括，而应结合程序静态结构进行分层分析。本文构建的实验框架和分析结果可为开发者选择适合 WebAssembly 的程序场景、为编译器与运行时优化定位重点瓶颈提供参考。

- WebAssembly 在浏览器外场景中的应用不断扩展，但其与 native 的性能差异仍需系统分析。
- 构建 native / Wasm JIT / Wasm AOT 三种运行模式；
- 使用内部计时获取连续性能比值；
- 基于 LLVM IR 与源码提取静态特征；
- 在 microbench 与 PolyBench kernel 上进行实验分析。
- 结论/贡献
  - 连续 ratio 比离散标签更适合分析性能差异；
  - PolyBench 上部分静态特征与性能差异存在较稳定关系；
  - Microbench 上性能差异更复杂，受多因素耦合作用明显；
  - AOT 未表现出稳定优于 JIT 的整体趋势。




## 绪论（引言）

### 1.1 研究背景与意义

- WebAssembly 的发展现状
- Wasm 在浏览器外、服务端、边缘计算中的应用
- native 与 Wasm 性能差异仍然是关键问题
- 为什么需要“结构可解释”的性能分析，而不仅仅是跑分对比

WebAssembly（Wasm）是一种面向安全沙箱环境的低级二进制指令格式，最初主要服务于浏览器内高性能应用的部署需求。随着运行时、编译工具链和 WASI 等生态的持续发展，Wasm 的应用场景已逐步扩展到浏览器外执行环境，包括服务端计算、边缘节点部署、插件化扩展和轻量级隔离执行等方向。相较于直接分发平台相关的原生二进制，Wasm 具有良好的可移植性、安全隔离能力和统一部署优势，因此正在成为连接多语言程序与多平台运行环境的重要中间形态。

然而，Wasm 在获得可移植性和安全性的同时，其运行性能是否能够接近 native 仍然是学术界和工业界共同关注的核心问题。已有研究表明，Wasm 在部分小型数值基准上能够接近原生代码，但在更复杂程序或不同运行环境中，其性能表现并不稳定，常常受到额外指令、访存开销、运行时实现和优化策略等多种因素影响。对于开发者而言，仅知道“Wasm 快还是慢”并不足以支撑技术选型，更重要的是明确：什么类型的程序更适合迁移到 Wasm，什么结构因素会导致 Wasm 相对 native 出现明显性能损失。

从现有研究现状看，Wasm 性能分析仍以整体跑分对比为主，即给出不同 benchmark 在不同运行模式下的总时间差异。这类工作对于回答“总体上 Wasm 是否接近 native”是有价值的，但对于解释性能差异背后的程序结构因素仍然不够充分。特别是在浏览器外运行模式下，Wasm JIT 与 AOT 两种执行方式与原生代码之间的差异，不仅体现为总体快慢差异，还可能与控制流复杂度、计算/访存比例、调用密度等静态结构特征相关。因此，开展一种面向程序结构、强调可解释性的性能分析具有现实意义。

基于此，本文尝试从“静态特征—性能差异”的角度对 WebAssembly 与原生代码进行实证研究。一方面，本文希望通过内部计时和连续性能比值构建更可靠的性能表征方式；另一方面，结合 LLVM IR 与源码信息提取程序静态特征，分析这些特征是否能够解释 Wasm 与 native 之间的性能差异。该研究不仅有助于理解 Wasm 在不同程序结构下的性能边界，也可为开发者进行技术选型、为编译器与运行时系统识别优化重点提供参考。

### 1.2 研究问题

建议明确写 3 个问题：

1. WebAssembly 与 native 的性能差异在不同程序结构下如何表现？
2. 程序静态特征是否能够解释这种性能差异？
3. Wasm JIT 与 AOT 是否表现出不同的性能特征与结构敏感性？


围绕上述背景，本文重点回答以下三个研究问题：

1. WebAssembly 与 native 的性能差异在不同类型程序中呈现出怎样的分布特征？在 microbenchmark 与规则数值 kernel 中，这种差异是否表现出一致规律？
2. 程序的静态结构特征能否解释 WebAssembly 与 native 之间的性能差异？哪些特征与连续性能比值具有更稳定的关系？
3. 在浏览器外运行场景下，Wasm JIT 与 AOT 两种执行方式是否表现出不同的性能特征与结构敏感性？

### 1.3 研究内容

- benchmark 构建
- 内部计时方案设计

- 性能差异分析
- 初步建模与案例分析



为回答上述问题，本文开展了以下几方面工作：

（1）构建实验框架。面向原生代码、Wasm JIT 与 Wasm AOT 三种执行模式，建立统一的 benchmark 编译、运行与结果汇总流程，并在相同环境下完成实验执行。

（2）设计性能测量方法。相较于仅使用外部 wall-clock 时间，本文优先采用 benchmark 内部计时方式，获得更贴近核心计算区域的执行时间，并进一步构造 `ratio_jit_over_native` 与 `ratio_aot_over_native` 等连续性能指标。

（3）构建数据集并提取静态特征。基于 microbenchmark 与 PolyBench kernel 两类程序，提取程序规模、控制流、调用密度、计算/访存比例等静态特征，形成用于后续分析的数据集。

（4）开展性能差异分析。基于相关性分析、连续 ratio 分析、多元回归和典型 case study，讨论哪些结构特征更容易导致 Wasm 明显劣于 native，哪些程序结构下 Wasm 可以接近甚至超过 native。

可以画流程图： `benchmark构建 → native/JIT/AOT运行 → 内部计时 → ratio计算 → 特征提取 → 统计分析`

本文采用“实验构建—特征提取—统计分析—案例解释”的研究路线。首先，选择 microbenchmark 与 PolyBench kernel 作为研究对象，分别代表局部机制导向程序与规则数值计算程序；随后，在 native、Wasm JIT 与 Wasm AOT 三种模式下运行基准程序，通过内部计时获得稳定的执行时间数据，并计算连续性能比值；接着，基于 LLVM IR 与源码提取静态程序特征；最后，通过相关性分析、多元回归与案例分析相结合的方法，对 Wasm 与 native 的性能差异进行解释。其总体技术路线可概括为：`benchmark 构建 → native/JIT/AOT 运行 → 内部计时 → ratio 计算 → 静态特征提取 → 统计分析与案例解释`。

## 相关技术与研究现状

### 2.1 WebAssembly 执行机制

- Wasm 基本模型
- JIT 与 AOT 的概念
- Wasmtime 运行时简介

WebAssembly（Wasm）是一种面向栈机模型设计的低级二进制指令格式，其核心目标是在保证安全性、可移植性与高效执行的前提下，为 C/C++、Rust 等语言提供统一的编译目标。Haas 等人在 PLDI 2017 的工作中指出，Wasm 被设计为一种与具体硬件、操作系统和浏览器解耦的低级表示，具有二进制紧凑、易验证、易编译以及便于网络传输等特点。这一设计使其既能够作为浏览器中的高性能执行格式，也具备向浏览器外扩展的潜力。

在执行机制上，Wasm 模块通常需要经过加载、验证、编译和执行等阶段。运行时会首先检查模块的类型安全与结构合法性，再将其翻译为目标平台机器码或中间表示后执行。与传统虚拟机不同，Wasm 采用线性内存模型和显式边界检查，以实现对宿主环境的隔离与保护，这一机制在增强安全性的同时，也可能引入额外的访存与边界检查开销。

当前主流 Wasm 运行时通常支持 JIT（Just-In-Time）与 AOT（Ahead-Of-Time）两类执行方式。JIT 模式在程序加载后动态编译并执行，更适合强调启动灵活性和运行时优化的场景；AOT 模式则在执行前将 Wasm 预编译为平台相关代码，以减少运行时编译开销。本文实验采用的 Wasmtime 是目前较为成熟的浏览器外运行时之一，具备较完整的 WASI 支持，并同时提供 JIT 与 AOT 能力，因此适合作为本文比较 WebAssembly 与 native 性能差异的实验平台。


### 2.2 WebAssembly 性能研究现状

- Wasm 与 native 性能比较的已有研究
- 浏览器内与浏览器外 Wasm 性能研究差异
- JIT/AOT 性能研究现状

围绕 WebAssembly 性能的研究，早期工作主要聚焦其作为 Web 端低级执行格式的可行性与效率。Bringing the Web up to Speed with WebAssembly 指出，Wasm 的提出是为了解决 JavaScript 作为编译目标时在性能和表达能力上的局限，目标是在安全、紧凑和可移植的前提下接近原生代码执行效率。随着浏览器实现不断成熟，Wasm 在部分数值基准和计算密集型场景中展现出接近甚至优于 JavaScript 的性能表现。

然而，后续研究表明，Wasm 与 native 的性能关系并不稳定。Not So Fast: Analyzing the Performance of WebAssembly vs. Native Code 通过在浏览器中对 SPEC CPU 和 PolyBenchC 等程序进行评测发现，Wasm 与 native 之间仍然存在显著性能差距，并指出额外的 load/store、branch 以及运行时安全检查是导致性能损失的重要原因。Understanding the Performance of WebAssembly Applications 则进一步说明，Wasm 的性能不仅受程序本身影响，也与编译器优化策略和执行环境密切相关，且某些传统 LLVM 优化在 Wasm 场景下未必总能有效转化为实际性能收益。

随着 WASI 和浏览器外运行时的发展，越来越多研究开始关注浏览器外的 Wasm 执行性能。Benchmarking Native Code Against WebAssembly in WebAssembly System Interface Compliant Environments 通过 Wasmtime、Wasmer 等运行时对多类程序进行对比，指出 Wasm 在系统调用、I/O 和内存管理相关场景下表现出较大的波动性，性能差异具有明显的 case-by-case 特征。这说明，在浏览器外环境中，Wasm 的性能分析不能仅依赖单一平均结论，而需要结合程序特征和运行模式进行更细粒度讨论。

从执行方式看，JIT 与 AOT 也是浏览器外 Wasm 研究的重要问题。一方面，AOT 通常被认为可以降低运行时编译成本；另一方面，其最终收益仍然依赖于运行时实现与程序结构特征。已有工作虽对不同运行时或不同模式做过对比，但针对 JIT、AOT 与 native 三者进行统一、可解释性能分析的研究仍较少，尤其缺乏将连续性能差异与程序静态结构联系起来的系统研究。


### 2.3 程序静态特征与性能分析相关研究

- 静态特征在性能分析中的应用
- 编译优化预测、程序建模中的典型特征设计

在性能分析与性能预测研究中，利用程序静态特征解释运行时行为是一条较为成熟的技术路线。相关工作通常从源码、控制流图、中间表示或指令统计中提取特征，用于分析程序复杂度、识别优化机会或预测程序在不同架构与编译选项下的表现。例如，基于静态分析的跨架构性能预测研究表明，程序规模、控制流结构和访存模式等信息能够为性能建模提供有效输入；在编译优化预测和程序表征学习领域，LLVM IR、基本块结构以及指令分布等也被广泛用作特征基础。

不过，已有静态特征研究大多面向传统 native 编译或跨架构性能预测，直接针对 Wasm 与 native 差异的分析仍较少。对于 Wasm 而言，程序性能不仅与一般意义上的计算密度、分支复杂度和访存比例相关，还可能受到线性内存模型、边界检查、寄存器利用受限以及运行时实现差异等影响。因此，面向 Wasm/native 性能差异的静态特征分析，需要在继承传统性能建模思路的基础上，结合 Wasm 执行特性重新选择和组织特征。

基于这一考虑，本文从 LLVM IR 与源码两个层面提取程序特征，重点关注程序规模、控制流复杂度、调用密度、计算密度以及计算/访存比例等指标，并尝试分析这些静态特征与连续性能比值之间的关系。与直接训练高精度预测器不同，本文更强调静态特征的解释价值，即识别哪些结构更容易导致 Wasm 性能劣于 native，哪些结构下 Wasm 更可能接近原生代码。


### 2.4 现有工作的不足与本文定位


这里可以写：

- 现有工作多关注总体跑分，缺少结构可解释分析
- 对 JIT/AOT 和 native 的统一比较仍不足
- 对 benchmark family 差异考虑不充分
- 本文工作聚焦内部计时与静态特征结合分析

综合已有研究可以发现，当前关于 WebAssembly 性能的工作主要存在以下不足。第一，许多研究以总体跑分或平均 slowdown 为主要结论，能够回答“Wasm 整体是否接近 native”，但难以进一步解释性能差异与程序结构之间的关系。第二，已有研究往往侧重浏览器内环境，或只比较 Wasm 与 native 的整体差异，对于浏览器外场景下 JIT、AOT 与 native 三者之间的统一分析仍然不足。第三，现有工作多使用单一 benchmark family 或单类程序，较少显式讨论 microbenchmark 与规则数值 kernel 在分析目标上的差异，从而容易将局部机制结论和整体结构结论混杂在一起。

基于上述不足，本文将研究重点放在“面向结构解释的性能分析”上。具体而言，本文不以单纯追求总体跑分或高精度预测为目标，而是构建统一的 native / Wasm JIT / Wasm AOT 实验框架，采用内部计时方式获得更可靠的连续性能指标，并结合静态程序特征对性能差异进行分析。通过同时使用 microbenchmark 与 PolyBench kernel 两类基准，本文尝试区分局部机制效应与规则计算程序中的结构规律，从而更细致地回答 Wasm 在什么条件下接近 native、又在什么条件下容易出现明显性能损失。
