# 增量阶段研究计划 Plan（5.21 后）

> 基于已有结论的进一步研究规划：从"发现规律"到"应用规律产出收益"，构建基于大模型的 WebAssembly 性能优化智能体（LLM-Agent）。

---

## 一、研究主线与定位

### 1.1 一句话定位
**基于大模型智能体的 WebAssembly 特定性能缺陷修复与优化框架**
（LLM-Agent for Wasm-specific Performance Bottleneck Refactoring）

### 1.2 研究路径
1. **Step 1 - 发现痛点（已完成）**：通过统计实验，建立"静态结构 → PMU 事件 → 运行时间"三段证据链，验证跨运行时一致性（wasmtime / wasmer）。
2. **Step 2 - 应用规律（本阶段）**：将统计规律作为"领域知识（Domain Heuristic）"，驱动 LLM Agent 对真实程序进行有针对性的代码重构，并通过编译-执行闭环验证收益。

### 1.3 核心创新点（论文卖点）
- **创新点 1**：首次系统揭示 Wasm 相对 Native 的 slowdown 与代码静态结构之间的可量化、跨运行时一致的相关性规律。
- **创新点 2**：基于该规律构建 LLM-Agent 框架，实现传统编译器（如 wasm-opt、LLVM PGO）无法做到的**语义级别代码重构**（如 if-else → 查表法、激进跨函数内联等），针对 Wasm 虚拟 ISA 的特定缺陷进行定向优化。
- **创新点 3**：提出"统计规律启发 + 编译执行闭环反馈"的优化范式，弥补单纯统计模型（如 Lasso R²≈0.55-0.80）预测精度不足、传统编译器规则僵化的双重缺陷。

## 二、关键决策（基于辩论的结论）

### 2.1 修改的层级：优先 LLVM IR，必要时回退或下探
| 层级 | 优点 | 缺点 | 决策 |
| --- | --- | --- | --- |
| C/C++ 源码 | LLM 理解最好 | 受 Clang/LLVM 黑盒干扰大，难做因果归因 | 仅作 sanity check 备份 |
| **LLVM IR (`.ll`)** | 保留类型/CFG/SSA 语义，LLM 可理解，绕过前端优化干扰 | 仍存在 backend Pass 干扰 | **主战场** |
| Wasm 字节码 / WAT | 最贴近最终产物，因果最干净 | 栈式汇编，LLM 改写极易破坏语义，重构空间小 | 作为最终下探备选 |

**对老师辩论的回应**：取折中方案，主战场选在 LLVM IR；同时保留 `wasm-opt` / WAT 局部 patch 作为对照实验，回答"是否直接改 Wasm 更纯粹"的质疑。

### 2.2 痛点定位：宏观 Lasso + 动静结合 Profiling
- **宏观层**：用已训练的 Lasso 模型，计算待优化程序在各特征上的"贡献度"（$w_i \times x_i$），找到该程序的"主要病因特征"。
- **微观层**：用 `perf record` / wasmtime profiling 找到耗时 Top-K 热点函数（80% 时间所在）。
- **交叉定位**：在热点函数内部，检查是否符合"病因特征"（如分支密度高 / 函数调用多），生成针对性诊断报告。

### 2.3 收益归因：四重证据
针对审稿人可能的"特征耦合扰动"质疑，准备多重证据：
1. **Lasso 贡献度差值分析**：计算 $\Delta \text{Slowdown}_{pred} = \sum_i w_i \cdot \Delta x_i$，证明目标特征的变化主导了预测降幅。
2. **对照基线**：与 `wasm-opt -O4`、Clang `-O3 + LTO` 等传统编译优化对比。
3. **Case Study**：挑选"指令数不降反升但时间变快"的反直觉案例，证明特定特征（如分支数）是主导因素。
4. **Prompt 受限性**：通过高度具体的 Prompt 约束 LLM 改动范围，将特征波动收束在目标维度。

## 三、增量任务清单（按优先级）

### Phase 0：手工 Proof of Concept（1-2 周）—— 最优先
**目标**：在不写框架的前提下，手工验证"改静态结构 → 时间变快"这条路走得通。

- [ ] **P0.1** 从现有数据集中筛选 3-5 个 slowdown 严重（≥1.5×）且静态特征高度集中（如 `function_count`、`cfg_edge_count`、`branch_density` 中至少一项显著偏高）的小型程序。
- [ ] **P0.2** 用 Clang 编译出 `.ll`，用 `wasm2wat` 导出 WAT，准备好两种表示形态。
- [ ] **P0.3** 手工挑一个程序：
  - 用 `perf` 或简单插桩定位热点函数。
  - 复制函数 IR 文本，配合诊断报告，喂给 GPT-4 / Claude 写 Prompt 让其重构。
  - 替换原 IR 中的对应函数，重新走 `llc -march=wasm32 → wasmtime / wasmer` 链路。
  - 测时间，记录是否变快、变快多少、其他特征是否符合预期变化。
- [ ] **P0.4** 写一份 1-2 页的 PoC 报告（含原 IR、改后 IR、特征对比表、时间对比表），向老师汇报，对齐技术路线。

> **退出标准**：至少 1 个程序在 wasmtime / wasmer 上获得 ≥10% 的运行时间下降，且语义检查（输出对比）通过。

### Phase 1：诊断器（Diagnoser）模块（2-3 周）

- [ ] **P1.1 全局诊断**：
  - 输入：编译产物 + Lasso 模型权重。
  - 输出：该程序排名 Top-K 的"病因特征"及其贡献度百分比。
- [ ] **P1.2 热点定位**：
  - 集成 `perf stat -e cycles,instructions,branches,L1-icache-load-misses ...` 或 wasmtime `--profile`，自动得到函数级耗时排名。
  - 输出：Top-K 热点函数列表。
- [ ] **P1.3 局部特征提取**：
  - 对 Top-K 热点函数，单独提取其局部静态特征（函数内基本块数、分支密度、调用数、循环嵌套深度等）。
  - 与全局病因交叉，输出"靶点函数 + 诊断标签"清单。
- [ ] **P1.4 Sanity Check**：在 PoC 中手动验证过的程序上跑诊断器，确认能自动找到同一个/同类靶点函数。

### Phase 2：Prompt 与 LLM 重构器（Refactor Agent）模块（2-3 周）

- [ ] **P2.1 Prompt 模板设计（按诊断标签分类）**：
  - 标签 A：控制流碎化（`cfg_edge_count` / `branch_density` 偏高）→ 模板要求使用 `select` / 查表法 / 循环展开消除分支。
  - 标签 B：函数调用密集（`function_count` 偏高）→ 模板要求激进内联融合相关函数。
  - 标签 C：基本块数偏高（`basic_block_count`）→ 模板要求合并 / 平铺基本块。
  - 标签 D：循环密集（`loop_count`、`loop_depth`）→ 模板要求循环展开 / 向量化（在 Wasm SIMD 可用时）。
  - 每类模板都需附带 "Wasm 性能背景知识 + 我们的统计结论 + 该函数的诊断报告" 三段上下文。
- [ ] **P2.2 LLM 选型与调用**：
  - 主选：GPT-4 / Claude 3.5 Sonnet，必要时对比 DeepSeek-Coder、Code Llama。
  - 接入 OpenAI / Anthropic / 本地模型 API，统一封装。
- [ ] **P2.3 输出解析与替换**：
  - 解析 LLM 返回的修改后 IR，自动定位并替换原文件中的对应函数。
  - 用 `llvm-as` / `llc` 检查 IR 语法合法性。

### Phase 3：闭环验证器（Validator）模块（2 周）

- [ ] **P3.1 编译流水线**：`.ll (modified) → llc → .wasm → wasmtime / wasmer 执行`。
- [ ] **P3.2 语义等价检查**：使用原程序输入/输出黄金对照（llvm-test-suite 自带的 `.reference_output`），自动比对结果。
- [ ] **P3.3 性能采集**：复用现有 perf 采集脚本（已有 perf 指标集），采集修改前后 8 项 PMU。
- [ ] **P3.4 反馈回路**：
  - 语法/语义失败 → 反馈错误日志到 LLM，迭代修复（设最大轮次 N=3-5）。
  - 性能未提升 → 反馈"实际 PMU 变化"到 LLM，要求换策略（如从标签 A 换到标签 B）。
  - 性能下降 → 回滚，记录失败案例。

### Phase 4：实验评估与论文写作（4-6 周）

- [ ] **P4.1 数据集扩充**：
  - 主数据集：LLVM test suite SingleSource 已有部分。
  - 补充数据集：PolyBench / Embench-IoT / 真实小型项目（如 zlib、json parser）。
  - 至少 50 个程序作为评估集。
- [ ] **P4.2 对照实验设计**：
  - Baseline 1：原始 Clang `-O3` 编译的 Wasm。
  - Baseline 2：`wasm-opt -O4` 后的 Wasm。
  - Baseline 3：传统 PGO（LLVM `-fprofile-use`）。
  - Baseline 4：LLM 无诊断的"盲改"（仅热点，无静态特征指导）—— 消融对照。
  - 本方法：诊断器 + LLM Agent 完整闭环。
- [ ] **P4.3 评估指标**：
  - 性能：运行时间下降率、PMU 事件下降率、相对 Native 的 slowdown 缩小幅度。
  - 框架代价：LLM 调用次数 / token 数 / 迭代轮次 / 编译时间。
  - 成功率：语义通过率、性能提升通过率。
- [ ] **P4.4 Case Study**：
  - 选 3-5 个典型程序深度分析。
  - 必备 1 个"指令数增加但时间下降"的反直觉案例，证明因果性。
- [ ] **P4.5 论文撰写**：
  - 主线：Motivation（已有结论作背书） → Design（Agent 架构图） → Implementation → Evaluation → Discussion。
  - 目标会场：ICSE / FSE / ASE / ASPLOS / PLDI（系统方向 + AI4Sys 子赛道）。

## 四、对老师与审稿人质疑的预案

### 4.1 老师关注：为何不直接改 Wasm 字节码？
- 回应方案：主框架在 LLVM IR 层面工作，但保留 WAT 层级的"局部 patch 路径"作为对比实验。如果某些极简优化（如分支布局调整）适合在 Wasm 字节码直接做，则用 WAT 路径，并对比两者收益。

### 4.2 审稿人质疑 1：你和 PGO 有什么本质区别？
- 回应要点（已在前期讨论中明确）：
  1. PGO 局限在"语法安全的局部模式匹配"，无法做语义级重构（如算法替换、数据结构重写）。
  2. PGO 面向物理 ISA，不针对 Wasm 虚拟机的特定开销（沙盒边界、间接调用）。
  3. LLM Agent 可以执行跨函数的激进结构改写，突破 Wasm 安全模型对 JIT 优化的限制。

### 4.3 审稿人质疑 2：你怎么证明收益来自目标特征，而非伴随的特征波动？
- 回应要点（四重证据）：
  1. Lasso 贡献度差值分解：$\Delta \text{Slowdown}_{pred} = \sum_i w_i \cdot \Delta x_i$。
  2. 与传统 `wasm-opt` / PGO 对照，证明"在指令数变化等同的情况下，本方法多收益的部分来自目标特征的改善"。
  3. Case Study 中的反直觉案例（指令数升、时间降）。
  4. Prompt 受限性确保了特征改动集中。

### 4.4 审稿人质疑 3：Lasso R² 只有 0.55，诊断器可靠吗？
- 回应要点：
  1. R² 0.55 在系统性能领域已属于强信号（存在硬件、运行时、调度等不可观测因素）。
  2. 诊断器不需"精准预测时间"，只需"对优化方向排序"，FDR 显著的特征已能稳定指引方向。
  3. 闭环试错机制本身就能容忍诊断噪声：诊断错了，闭环会反馈失败、切换策略。

### 4.5 审稿人质疑 4：LLM 的不确定性 / 不可复现性怎么办？
- 回应要点：
  - 固定随机种子 / temperature=0。
  - 多次重复实验，报告均值 + 方差。
  - 对每个 Case Study 提供完整的 Prompt + LLM 输出存档。

## 六、风险与备选方案

| 风险 | 备选 |
| --- | --- |
| LLM 改 IR 语义破坏率高 | 退回到 C 源码层（接受 Clang 干扰，用更严格的对照实验弥补） |
| 诊断器 Lasso 在新数据集上失效 | 重新训练；或退化为"纯热点+经验规则" |
| 收益不显著（<5%） | 聚焦特定子领域（如 numeric / control-flow heavy 程序），讲清"对哪类程序有效" |
| LLM API 成本爆炸 | 用本地小模型（Code Llama 7B / DeepSeek-Coder）+ 微调 |
| 老师坚持 Wasm 字节码 | 双轨并行：IR 主线 + WAT patch 副线，最终在论文中分别报告，让数据说话 |
