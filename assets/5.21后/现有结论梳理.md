现有初步结论：
1. 时间比跟哪些动态指标同步
wasm 相对 native 越慢，越倾向于出现 更多相对 cpu_cycles，更多相对 instructions_retired，更多相对 iCache_load_misses，更多相对 branches_retired 等执行路径变重的信号。
而ratio_all_loads_retired_over_native / ratio_all_stores_retired_over_native 与时间比在 FDR 下 未显著，这说明 wasm 慢的主要原因是 其需要执行更多指令，占用更多 cpu 周期。
 -> wasm 的指令翻译/代码生成质量有问题，或者 wasm 运行时引入了额外的执行开销。
2. 代码结构先落在哪些 PMU 比值上
- 控制流 / CFG 密度（如 basic_block_count、branch_instr_count、cfg_edge_count、branch_density）与 ratio_all_stores_retired_over_native、ratio_all_loads_retired_over_native 呈 强负秩相关（|ρ| 约 0.52–0.58，FDR 显著）。
可能的解释： 控制流碎 → Native 访存优化受限 + Wasm 控制流开销激增 → 访存的相对膨胀被"淹没"在其他事件的更大膨胀中 → 访存比值显得"低"
不过真正驱动 slowdown 的是周期和指令的绝对膨胀，而非访存。因此，虽然静态结构能"预测"访存比值，但访存比值本身不传递到时间差距——它是链条中的一个"被旁路"的中间节点。
- memory_access_density 与 ratio_branches_retired_over_native（ρ≈−0.54）、ratio_instructions_retired_over_native（ρ≈−0.53）等 FDR 显著。
可能的解释：访存密度高的程序通常是"大循环、规则计算"型 workload（如矩阵运算），这类程序 Native 版本分支本来就少、且编译器会做循环展开/向量化增加指令，因此 Wasm/Native 的分支/指令比值膨胀空间有限。负相关不是"访存抑制了分支数/指令数"，而是"程序类型差异导致的统计共变"。
- function_count 与 ratio_cpu_cycles_over_native 呈 正秩相关（ρ≈0.52，FDR 显著）。
可能的解释： 函数切分越多，调用次数越多，而 Wasm 的每次函数调用都要经过函数表查找、类型检查、边界验证等运行时步骤，这些固定开销随调用频率线性累积，导致相对周期膨胀。Native 编译器可以通过内联消除这种开销，但 Wasm 的安全模型限制了跨函数优化，因此函数数量直接成为 Wasm 性能敏感因素之一。
3. 静态特征 与 运行时间比 的直接关联分析
- 正相关：function_count（ρ≈0.50）、compute_instr_count（≈0.44）、ir_instruction_count（≈0.43）、loop_count（≈0.40）、basic_block_count（≈0.35）等 → 规模与计算/控制流体量 越大，时间比越倾向于更大。
- 负相关：memory_access_density（ρ≈−0.37，FDR 显著）→ 与「访存密则更慢」的口语直觉不同，说明链头不能单句概括；正文应写明 「单变量秩相关」 并引用链腰中与 perf 的联合模式，避免误读为因果。
 联合解释：
- 在单变量秩相关层面，memory_access_density 与内部时间比呈负相关（Spearman ρ≈−0.37，FDR q<0.05），即控制其他变量后，访存密度高的程序倾向于时间比更低。然而，这一关系需结合链腰中与 perf 的联合模式理解：访存密度高同时与分支退役比、指令退役比负相关（ρ≈−0.54/−0.53），而这些 perf 比值才是时间差距的强预测因子（ρ≈0.66/0.80）。因此，访存密度并非时间差距的直接驱动，而是标记了一类'分支少、指令膨胀有限'的 workload。"
总结：用统计方法证明了：Wasm 比 Native 慢，主要不是因为"访存变差"，而是因为"同样逻辑执行了更多指令、花了更多 CPU 周期"。代码结构通过这条"指令膨胀→周期膨胀→时间变慢"的链条间接决定性能差距。因此，优化 Wasm 应该优先关注代码生成质量和运行时开销削减，而非访存优化。

Wasmer 结论总结：
换了另一个 Wasm 运行时（wasmer）重新做了一遍实验，发现之前 wasmtime 上发现的"静态结构 → 性能事件 → 时间差距"三段式规律依然成立，而且 wasmer 上这个规律表现得更明显、更强烈。
结论 A'：时间差距跟哪些硬件事件同步？
Wasm/Native 时间比与 cpu_cycles / instructions_retired / L1_icache_load_misses / branches_retired 四类 perf 比值高度同向。
Wasm 越慢，越是因为"花了更多 CPU 周期、执行了更多指令、I-cache 取指更费劲、分支更多"。
wasmer 的新发现：wasmer 上还额外发现了 "条件分支" 和 "分支预测失败" 也显著相关。
意义：不同运行时在同一个规律上表现一致，但 wasmer 把某些"边缘显著"的信号压到了"强显著"——说明这不是某个运行时的偶然，而是 Wasm 的结构性问题。

---
结论 B'：代码结构哪些特征能预测慢？
12 个静态特征通过 FDR 显著，按相关强度排序：函数数、IR 指令数、计算指令数、循环数、基本块数……
程序越大、函数越多、循环越多、控制流越复杂，Wasm 相对 Native 越慢。
关键对比：wasmer 上比 wasmtime 多出了 6 个"边缘特征"变成显著，但所有特征的方向（正相关/负相关）与 wasmtime 完全一致。
意义：规律方向稳定，只是 wasmer 上信号更强。
但相关性都不算特别强，最高的约为 0.57，只能算中等强度
但这些特征的相关性都通过了 FDR 显著
这说明"代码结构确实系统性地影响 Wasm slowdown"这一信号是真实的（不是偶然），但代码结构只是 slowdown 的部分原因——其他因素（运行时机制、硬件特性、程序类型混杂）也贡献了显著方差。
相关性不高 —— 因为静态特征只是 slowdown 的部分原因

---
结论 C'：代码结构如何"碰到"运行时？
控制流/CFG 类静态特征与 访存退役比 的强负相关在 wasmer 上全部复现且系数更大；同时 平均基本块大小、函数数 等与 I-cache miss 比 的连接更强。
代码控制流越"碎"，Wasm 的访存相对膨胀越被"压制"，但 I-cache 取指效率越差。这条"控制流碎 → I-cache miss 增加 → 时间变慢"的链条，在 wasmer 上比 wasmtime 更明显。
与 wasmtime 的关系：同一条三段链，wasmer 上耦合更紧。

---
结论 D'：用代码结构能多大程度上预测慢？
Lasso 稀疏线性模型 R² = 0.804（解释 80% 方差），10 个非零特征。
只看代码结构（不看实际运行），就能预测 Wasm 会慢多少，准确度约 80%。
关键对比：wasmtime 上只能解释 55%，wasmer 上能解释 80%。
意义：不是模型变好了，而是 wasmer 的时间差距对代码结构更敏感——同样的代码特征，在 wasmer 这条管线里被放大了。

---
结论 E'：跨运行时一致性
wasmtime 与 wasmer 的时间比 Spearman ρ = 0.923；静态-时间相关序列 ρ = 0.972；perf-时间相关序列 ρ = 0.929。
两个完全不同的运行时，对同一个程序集给出的"谁快谁慢"排序几乎完全一致（92%）；静态特征与快慢的关联模式也几乎完全一致（97%）。
核心总结：
"静态 → perf → 时间" 三段证据链不是某个运行时的偶然，而是跨运行时可复现的通用规律。
