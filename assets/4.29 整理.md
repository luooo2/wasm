## 1) 内部计时 / 外部计时是怎么采集的

当前流程是 `build_llvm_direct.py` + `run_llvm_from_runnable.py` 配合完成的：

- **内部计时（internal）**
  - 在 `src/llvm_timing_wrapper.c` 里，`main()` 在调用 `llvm_bench_main()` 前后用 `clock_gettime(CLOCK_MONOTONIC)` 取时间差，打印 `TIME_NS:<ns>`。
  - `run_llvm_from_runnable.py` 用正则 `RE_TIME_NS` 从 stdout/stderr 里抓这个值，换算成 `internal_ms`。

- **外部计时（external）**
  - `run_llvm_from_runnable.py` 的 `run_once()` 在 Python 侧用 `time.perf_counter()` 包住 `subprocess.run(...)`。
  - 这个时间包含了进程启动、运行时装载、IO 等端到端开销，记成 `external_ms`。

你代码里这两段分别对应了上面两件事：

```13:18:src/llvm_timing_wrapper.c

    int rc = llvm_bench_main();
    uint64_t t1 = nsec_now();

    return rc;
}
```

## 2) `src/llvm_timing_wrapper.c` 的作用

核心作用有 3 个：

- 统一入口：把原 benchmark 的 `main` 重命名为 `llvm_bench_main`，wrapper 提供统一 `main`。
- 统一计时口径：native 与 wasm 都走同一段内部计时代码。
- 可自动解析：输出固定格式 `TIME_NS:...`，便于脚本批处理抽取。

在构建脚本里也明确这么做了（先 `-Dmain=llvm_bench_main`，再和 wrapper 链接）。

## 3) wrapper 会不会影响 perf 数据？

**会有影响，但通常是“可控且可消除”的小影响。**

- 影响来源：
  - 多了 `clock_gettime` 两次 + `printf` 一次；
  - 额外引入一点指令、分支、syscall/libc 路径；
- 但你现在做法的优点是：
  - native 与 wasm 都加了同一个 wrapper，**对比时有一定抵消**；
  - 对长时间程序影响比例较小，对超短程序影响会更明显。

更严谨建议（你后续可以这样做）：

- **计时实验**：保留 wrapper（需要 `TIME_NS`）。
- **perf 实验**：使用“无 wrapper 构建”单独跑一版 perf（最干净）。
- 如果暂时不拆两套构建，至少做个 sanity check：随机抽 5 个程序，比较有/无 wrapper 的关键 perf 事件差异占比。

## 4) 静态特征怎么提取？“static branches vs perf branches”会不会冗余？

### 怎么提取静态特征
你现在已经输出 `.ll`（LLVM IR），非常适合从 IR 提特征。建议两层：

- **基础密度类**（函数/模块级）
  - `#br / #inst`, `#load / #inst`, `#store / #inst`
  - basic block 数、平均块大小、CFG 边密度
- **结构复杂度类**
  - 循环层数（loop depth）、回边数、`phi` 节点密度
  - 间接调用密度、函数调用深度 proxy

第一版不必上自定义 pass，可先用 `opt` 分析输出 + Python 解析 `.ll`，先跑通。

### 会不会“branches 对 branches”很冗余？
**不冗余，前提是你明确它们语义不同：**

- 静态 `branches`：代码里“潜在分支位点/结构复杂度”（编译前结构信号）。
- perf `branches-retired`：运行时“实际执行了多少分支”（输入/路径/运行时行为信号）。

它们正好可以形成“结构 -> 动态行为 -> 性能后果”的链条。  
真正要避免的是“同义重复特征”，比如同时放太多线性相关的静态计数。可用相关性筛一轮（Spearman/VIF）。
